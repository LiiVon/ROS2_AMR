# ROS2 AMR 18 个包学习与复刻顺序

本文档用于逐包学习和手写复刻当前项目，不是一次性搭建最小闭环的开发计划。

核心原则：

1. 从无 C++/ROS 依赖的接口包开始。
2. 从纯数据、纯算法和纯配置开始，再接 ROS 节点。
3. 一次只完成一个包，并让其单独构建通过。
4. 每完成一个包，验证其依赖关系、测试和最小运行方式。
5. 仿真、导航、任务和顶层编排放在基础包之后。
6. 动手前先用现成代码把系统完整跑一遍，知道每一步要复现的“目标行为”。
7. 每个包都走同一个循环：黑盒运行 → 读依赖 → 通读源码 → 关掉源码默写 → 与原实现 diff → 构建/测试 → 提交。

## 〇、第 0 步：先黑盒跑通原工程

在写第 1 个包之前，**先不要读源码**，用现成代码把系统完整跑一遍，建立“目标行为”基线。
复刻时如果不知道正确表现，默写完也无从判断对错。

```bash
source /opt/ros/jazzy/setup.bash
colcon build --base-paths src --symlink-install
source install/setup.bash

# 最小闭环：mock 底盘 + 传感器 + 安全链 + 诊断
ros2 launch robot_bringup bringup.launch.py backend:=mock

# 无界面自动仿真演示（Gazebo + 自动任务链）
ros2 launch robot_bringup amr_demo.launch.py gui:=false use_rviz:=false
```

只观察，不读实现：

| 观察项 | 命令 / 方式 | 要记住的结论 |
|---|---|---|
| 节点与话题全貌 | `rqt_graph` | 每条链路上谁连谁 |
| `/cmd_vel` 唯一性 | `ros2 topic info /cmd_vel -v` | 发布者只能有一个（`robot_teleop`） |
| 关键话题 | `ros2 topic list` | `/odom`、`/scan`、`/system/health`、`/diagnostic` |
| 接口契约 | `ros2 interface list` / `ros2 interface show` | 7 个接口包覆盖哪些域 |
| 服务入口 | `ros2 service list` | `/business/*`、`/mission/*` |
| 仿真形态 | `amr_demo.launch.py gui:=true` | 站点、设施、机器人走位 |

产出：一张手画的话题/服务草图 + 一页“目标行为清单”。
之后每复刻一个包，都拿着这张图问自己：“这个包在图里的哪条边上？”

## 一、推荐总顺序

```text
核心接口
  → 专业领域接口
  → 机器人模型和工具
  → 底盘、传感器、安全
  → 路径跟踪和导航
  → 仿真
  → 指标和任务
  → 顶层编排
  → 工具链（规范检查贯穿全程；冒烟与操作台最后做）
```

> **7 个接口包不要用同一强度精读。**
>
> - 第 1 步 `robot_interfaces_core` 精读：字段语义、单位和默认值、`rosidl_default_generators`、
>   生成物与引用方式、`ros2 interface show` 全流程。
> - 第 2~7 步用“速通”模式：看职责 → 浏览 msg/srv/action 名字与字段 → 建包 → 构建 →
>   `ros2 interface list | grep robot_interfaces_` 确认，每个包控制在 1 天以内。
>   领域语义（任务状态、设施预约、订单履约）留到第 17 步 `robot_tasks` 真正用到时回查——
>   带着使用场景回看契约，效率远高于一次性背完。
>
> **两个里程碑，到了就停下来做一次联调：**
>
> - 第 12 步 `robot_teleop` 完成后：mock 底盘 + 传感器 + 安全链 + 诊断第一次组成可运行竖切，
>   完整跑一次、重画话题图、确认 `/cmd_vel` 只有一个发布者。
> - 第 15 步 `robot_simulation` 完成后：整机可以在 Gazebo 里跑，后面任务中枢才有真实联调环境。
>
> **参考节奏（按每天 2~3 小时业余学习估算，宁慢勿快）：** 接口阶段约 5~7 天；
> 第 8~12 步约 2~3 周（`robot_hardware` 占大头）；第 13~15 步约 2 周；第 16~18 步约 1~2 周。

> `tools/` 下不是 colcon 包，不参与上面 18 步的构建顺序，但复刻时同样要写：
> 其中 `check_conventions.py` **第一阶段就要有**（每完成一个包都用它自检），
> 其余的冒烟、HTTP 网关、操作台页面与北向适配器放在 18 个包全部完成之后，详见第四节。

## 三、逐包学习内容

### 1. `robot_interfaces_core`

职责：

- 定义机器人、底盘、任务、导航统计和跟踪误差消息；
- 定义统计查询、底盘模式和控制模式服务；
- 作为跨包共享的核心接口。

复刻重点：

- 了解 `.msg` 和 `.srv` 的字段语义；
- 统一单位和默认值；
- 学习 `rosidl_default_generators`；
- 学习包内接口名称的生成与引用。

验收：

```bash
colcon build --base-paths src --packages-select robot_interfaces_core
source install/setup.bash
ros2 interface show robot_interfaces_core/msg/ChassisState
```

### 8. `robot_description`

职责：

- 提供 URDF/xacro；
- 定义底盘、轮子、激光、IMU 和 camera 等几何关系；
- 提供 RViz 模型配置。

复刻顺序：

2. 差速或麦轮轮子；
3. `lidar_link`、`imu_link`；
4. `base_footprint`、`base_link`；
5. Gazebo 插件或仿真参数；
6. RViz 配置。

需要掌握：

- xacro 宏；
- 坐标系定义；
- 关节名称；
- 轮径、轴距、轮距；
- URDF 到 TF 的关系。

验收：

```bash
colcon build --base-paths src --packages-select robot_description
```

> **注意：** `display.launch.py` 属于第 18 步的 `robot_bringup`，第 8 步时还不可用。
> 复刻时先在 `robot_description` 包内写一个最小 `launch/display.launch.py`
> （xacro 展开 → `robot_state_publisher` → `rviz2 -d rviz/display.rviz`），
> 并在 `CMakeLists.txt` 的 `install(DIRECTORY ...)` 里加上 `launch`。这是第 8 步的验收入口；
> 到第 18 步再把顶层显示/演示 launch 收拢进 `robot_bringup`——
> 正好体会“包内最小 launch”与“顶层编排 launch”的分工。

```bash
# 包内最小验收（自己写的 launch）
ros2 launch robot_description display.launch.py

# 或只校验模型本身：xacro 展开 + URDF 解析（需已安装 liburdfdom-tools）
PREFIX=$(ros2 pkg prefix robot_description)
xacro "$PREFIX/share/robot_description/urdf/robot.urdf.xacro" \
  geometry_file:="$PREFIX/share/robot_description/config/robot_geometry.yaml" \
  > /tmp/robot.urdf

```

> **第 14 步时 TF/odom/scan 还没有真实来源**（`robot_hardware` 的 mock 可以发 `/odom`，
> 但真实世界在第 15 步）。两种做法选一种：
>
> - **方案 A（默认，本文档按此编号）**：用替身先把 Nav2 生命周期和参数跑通——
>   固定地图 + 静态 `odom→base_link` 替身 + 可缺省的 `/scan`；缺 TF/扫描的告警属于预期，
>   只要节点列表齐全、能完成 configure/activate 的节点都在 `active` 即算通过。
> - **方案 B**：把第 15 步 `robot_simulation` 提前到第 13 步之后，
>   先有世界和真实 TF/scan 再配 Nav2。总工作量相同，适合更想先理解仿真的人。
>
> 方案 A 的最终验收仍然要等第 15 步仿真起来后补做一次：用真实 TF/scan 跑
> `ros2 launch robot_navigation nav.launch.py`，确认能规划并执行到目标点。

验收（方案 A）：

```bash
colcon build --base-paths src --packages-select robot_navigation
```

## 四、tools 工具链（第 19 步，18 个包之后）

先回答一个常见疑问：**`tools/` 下的脚本不能全部留到最后一起做**，它们是两类东西。

| 文件 | 什么时候复刻 | 需要哪些包已可用 | 作用 |
|---|---|---|---|
| `tools/check_conventions.py` | **第一阶段（写完第 1 个包就要有）** | 无（只用 Python 标准库） | 命名/行数/分层门禁，每包自检用 |
| `tools/smoke_mission.sh` | 第 10、12、17、18 步都完成之后 | `robot_hardware`、`robot_teleop`、`robot_tasks`、`robot_bringup` | 端到端业务冒烟（下单→暂停→恢复→快照） |
| `tools/operator_api.py` | 最后：18 个包全部完成、业务服务齐全后 | `robot_interfaces_business`、`robot_tasks` | HTTP ↔ ROS 2 服务网关（不含业务逻辑） |
| `tools/front_end.html` | 与 `operator_api.py` 同一批（先定端点，再写页面） | `tools/operator_api.py` 的端点契约 | 零依赖操作台页面 |
| `tools/smoke_operator_api.sh` | 与网关同批 | `tools/operator_api.py` + `robot_bringup` + `robot_tasks` | 14 个 REST 端点冒烟（健康/车队/设施/事件/批量下单/重排/400） |
| `tools/adapters/*` | 网关完成后 | `robot_interfaces_business`、`_mission`、`_facility`、`_fleet` | VDA5050 file/MQTT/即时动作、PLC、外部回调 |

要点：这些最后的脚本都**只调用已有能力**，不新增业务逻辑。
反过来先写页面/网关，就会被迫去改接口包和任务中枢来迁就前端——顺序必须是从服务到网关再到页面。

`tools/` 不参与 `colcon build`，但 `check_conventions.py` 通过 `robot_bringup/CMakeLists.txt`
里的 `conventions` 测试进入了 `colcon test` 门禁，所以它必须最早存在。

### 4.1 `tools/check_conventions.py`（第一阶段）

复刻要点：

1. 用 `argparse` 提供 `--root`（默认 `src`）与 `--strict`；
2. 四类检查：
   - 命名：禁止版本号前缀式命名（标识符/路径）、`_srv`/`_pub`/`_sub` 缩写、`data_`/`tmp_` 占位名；
   - 行数：单文件 ≤ 1500 行（`--strict` 时超限也算失败）；
   - 分层：`include/<包名>/` 与 `src/` 根层不得堆放散装 `.hpp/.cpp`；
   - 扩展名：实现片段统一 `.inc`。
3. **必须校验 `--root` 是目录**，否则路径写错时会“零命中 → 假通过”；
4. 匹配前剥掉块注释与字符串，避免 `/* */` 和字符串里的 `_pub` 误报。

验收：

```bash
python3 tools/check_conventions.py --strict         # 退出码 0
python3 tools/check_conventions.py --root /tmp/nope # 退出码非 0（防止假通过）
```

### 4.2 `tools/smoke_mission.sh`（第 18 步之后）

复刻要点：

1. `set -eo pipefail`；`source` ROS 环境时临时 `set +u`（setup.bash 会引用未定义变量）；
2. 用 `setsid` 启动 launch 并记录 PID，退出时 `kill -TERM -<pid>` 杀**整个进程组**再 `wait`；
   只 kill 父进程会留下 bringup 的子节点，污染后续 `colcon test`（真实踩过：残留节点会让 launch 测试误判）；
3. 临时日志写入 `/tmp`，`trap` 中清理；
4. 不用固定 `sleep`，改为有界轮询等待服务/话题出现；
5. 断言链路：下单成功 → 暂停成功 → 恢复成功 → 快照可读，最后打印唯一成功标志 `SMOKE PASSED`。

验收：

```bash
tools/smoke_mission.sh    # 末尾输出 SMOKE PASSED、退出码 0；/tmp 无残留日志
```

### 4.3 `tools/operator_api.py`（最后）

复刻要点：

1. 只用标准库 `http.server` + `rclpy`，不引入 Web 框架；
2. rclpy 节点在独立线程里 spin（`MultiThreadedExecutor`），HTTP 线程同步调用服务；
3. 每个端点都是**一对一映射**，不写业务判断：

   | 方法 | 路径 | 对应 ROS 服务 |
   |---|---|---|
   | GET | `/` | 返回同目录 `front_end.html` |
   | GET | `/api/health` | 网关/页面就绪状态 |
   | GET | `/api/operator/snapshot` | `/business/get_operator_snapshot` |
   | POST | `/api/business_orders` | `/business/submit_order`（`order_type=business`） |
   | POST | `/api/workflows/{pause,resume,cancel}` | `/business/{pause,resume,cancel}_workflow` |

4. 状态码约定：服务不可达/超时 → 503；缺参数 → 400；其他异常 → 500，且都返回 JSON；
5. 业务拒绝（如路径锁被占）不能伪装成失败：把 `message` 原样回传给页面；
6. 记住实现约定：业务单展开后工作流 id 是 `business_<业务单号>`，页面据此填暂停/取消单号。

验收：

```bash
python3 tools/operator_api.py --port 18080 &
curl -s localhost:18080/api/health
curl -s "localhost:18080/api/operator/snapshot?event_limit=5"
curl -s -X POST localhost:18080/api/business_orders -H 'Content-Type: application/json'
curl -s -X POST localhost:18080/api/workflows/pause -d '{"order_id":"business_cli_1"}'
```

### 4.4 `tools/front_end.html`（与网关同批）

复刻要点：

1. 单文件、零依赖，纯 `fetch` 调 REST，不直接连 ROS；
2. 所有插入文本必须转义（`escapeHtml`）后再写 `innerHTML`，否则接口返回的 message 可注入标签；
3. 提交后自动把返回的 `workflow_order_id` 填进暂停/取消输入框；
4. 成功与失败分开提示：`success=false` 时显示“业务工单被拒绝：<message>”，不要显示“已提交”；
5. 可选自动刷新（5 s），刷新失败不得清空已有表格。

验收：

```bash
# 浏览器打开 http://127.0.0.1:18080/
# 提交一单 → 看到 mission_ids 与队列变化 → 暂停 → 恢复 → 取消，均无报错
```

## 五、每个包的复刻模板

顺序本身不是关键，**每个包都走同一个循环**才是关键。

### 5.1 复刻前：先当用户，再当作者

1. **黑盒运行**：用原实现单独跑一次该包（包内有 launch 就用包内 launch；
   没有就借用上一阶段已复刻的包拼一个最小场景）。
   `ros2 node info`、`ros2 topic echo`、`rqt_graph` 各看一遍，记下“目标行为”。
2. 读 `package.xml` → `CMakeLists.txt` → 目录结构，画一张“本包依赖谁、被谁依赖”的草图。
3. 通读源码，标出纯算法/纯数据与 ROS 装配的边界（本项目刻意分层：`core/`、`model/`、`workflow/`、`nodes/`）。
4. 写清楚本包的最小验收命令：一条构建、一条测试、一条可观察的运行现象。

### 5.2 复刻时：关掉源码默写

5. 手写包骨架：`package.xml`、`CMakeLists.txt`、`include/<package>/`、`src/`、`test/`、`README.md`。
6. 先写纯数据或纯算法，再写类和库接口，再接 ROS 参数、topic、service 或 action。
7. 为核心逻辑写 gtest，单独构建、单独测试。
8. 最后接入上游包。

### 5.3 复刻后：diff 与沉淀

9. **对照原实现 diff**：重点不是格式，而是你漏掉的边界条件——超时、饱和、`frame_id`、
   生命周期、异常路径。每一条漏掉的条件都记进笔记。
10. 回到第 0 步的“目标行为清单”，确认本包对应的那一行行为已经对上。
11. 提交代码（`learn/<包名>` 分支或独立目录均可），写 5 行“我学到了什么 / 哪里踩了坑”。

不要一上来复制整个包。每次只复刻一个目录或一条数据链。

## 六、单包学习的退出标准

一个包不能只“代码写完”就算完成，应满足：

## 八、复刻时必须遵守的硬约束（本次修复沉淀）

按前面的顺序复刻时，以下行为**不是可选项**——它们都是实际排查出来的缺陷，复刻时若省略会直接复现同样的 bug。
每条都注明了对应的验证方式，完成某一步后请立即验证。

### 8.1 安全链路（第三阶段：`robot_teleop`）

| 约束 | 反面教材（已修复的 bug） | 验证方式 |
|---|---|---|
| 限速只降速，不得写 `stop_reason` | 把限速提示写进停车原因 → 一下发限速机器人就原地停死 | 设 0.2 m/s 限速后 `safety_stop=false` 且 `/cmd_vel` 被限幅 |
| 角速度限幅与线速度限幅相互独立 | 线速度限值为 0 时提前 `return`，角速度上限永远不生效 | `angular.z=3.0` + 无线速度限值 → 输出被 clamp 到 0.6 |
| 急停/解除严格分离 | `enable_emergency_stop` 传 `data=false` 成了隐藏解锁通道 | 四个方向（enable/clear × true/false）逐一测试 |
| 遥控必须有 deadman | 接管后每 50 ms 重发缓存指令，上游崩溃后车继续跑 | 停发 `/cmd_vel/virtual_rc` → 300 ms 内 `/cmd_vel/teleop` 归零 |
| 接管锁必须有限超时 | `timeout: 0.0` 导致接管进程退出后导航被永久屏蔽 | kill 接管节点 → 1 s 内 nav2 指令恢复生效 |
| 健康监控要有新鲜度 | 只看最后一条 `/system/health`，监控进程死掉后一直判 CLEAR | kill `system_monitor_node` → 进入 FAULT |

### 8.2 底盘与传输（第三阶段：`robot_hardware`）

| 约束 | 反面教材 | 验证方式 |
|---|---|---|
| 串口读要把 `EAGAIN` 当“没数据” | 非阻塞串口每 20 ms 报一条读失败 | 停机观察日志无 `Resource temporarily unavailable` |
| 串口写必须整帧写出 | 短写被当成功，底盘侧解析失步 | 注入短写场景后指令仍完整 |
| 入口拦截 NaN/Inf 指令 | 非有限值进入积分 → `EstimateWheelSpeeds` 抛异常 → 驱动节点退出 | 注入 `linear.x=NaN` 后节点存活、`/odom` 无 NaN |
| ros2_control 必须上报链路故障 | `read()` 恒返回 OK，断链后位置继续漂移 | 断开 UDP 对端 → 上报 ERROR 且位置冻结 |
| `write()` 不得让异常穿透 | 一次异常终止 controller_manager | 注入非法轮速 → 返回 ERROR 而不是崩溃 |
| 清零必须下发到底盘 | 只清本地，下一帧被底盘覆盖，`/odom` 与 `/wheel/odom` 分裂 | 清零后两者都归零且不回跳 |

### 8.3 传感器（第三阶段：`robot_sensors`）

| 约束 | 反面教材 | 验证方式 |
|---|---|---|
| 字节流必须做跨消息缓冲 | 边界判错一位 + 无缓冲，单帧消息永远解析不出 | 构造「一帧一条 / 两帧一条 / 一帧跨两条」三种输入 |
| 反转扫描必须重写角度元数据 | 只 `reverse` 数组，扫描被镜像 | 顺时针激光下障碍物方位角与索引一致 |
| 滤波器要么真过滤，要么别叫 filter | 名为 filter 实际只转发 + 每帧刷诊断 | 代码审查 + 诊断频率 |

### 8.4 跟踪与导航（第四阶段）

| 约束 | 反面教材 | 验证方式 |
|---|---|---|
| Stanley 输出的是角速度 | 把转向角 δ 直接写进 `angular.z`，量纲错误 | `ω = v·tan(δ)/L`，`v≈0` 单独处理 |
| `actual_speed` 取实测值 | 填成刚发出的目标速度，实验数据全失真 | 目标 0.35 / 实测 0.10 → 消息里是 0.10 |
| 控制器要判 odom 新鲜度与坐标系 | 断流后继续用旧位姿发速度 | 停发 `/odom` → 300 ms 内输出零速 |
| Pure Pursuit 曲率分母用实际距离 | 用配置预瞄距离 `Ld`，目标点比预瞄近时曲率被低估 | 与标准式 `2·sinα/Ld_actual` 对比 |
| 区域文件缺失要报错 | 静默返回空集，keepout 无声失效 | 删除 zones 文件 → `config_valid=false` |

### 8.5 任务中枢（第五阶段：`robot_tasks`）

| 约束 | 反面教材 | 验证方式 |
|---|---|---|
| 取消工作流必须清暂停集合 | 暂停后取消，再提交同名单被永久跳过 | 下单→暂停→取消→同号重投→正常执行 |
| 派发失败必须回到队列 | action server 未就绪时任务静默丢失、队列不再启动 | 先起任务中枢、3 s 后起导航服务器 → 自动恢复 |
| 路径锁在派发时获取 | 提交即占锁，同走廊批量订单必然部分失败 | 同走廊连下 3 单全部接受并串行执行 |
| goal 接受窗口内的取消不能丢 | 取消被 `BeginMission` 重置后任务照常执行 | goal 发出后 10 ms 内取消 → 进入 CANCELED |
| 运输任务也能暂停/恢复 | 用 `mission_active_` 判定，运输期间拒绝暂停 | 运输各阶段 pause/resume 成功 |
| 导航服务器共享状态要加锁 | detached 线程与执行器线程无锁读写 | 压测 100 次含取消/暂停的 goal 无异常 |
| 等待必须有超时 | `WaitForFuture` 无超时会永久占用 `active_` | Nav2 不响应时任务失败而不是卡死 |
| 暂停要先等取消落地 | 不等取消完成就重发目标，被 Nav2 拒绝 | 连续 3 次暂停/恢复仍能到达终点 |

### 8.6 评测与编排（第五/六阶段）

| 约束 | 反面教材 | 验证方式 |
|---|---|---|
| 统计字段按 msg 语义填 | 成功率恒 1.0、里程填成误差和、耗时填成弧度 | 已知场景（2 目标 1 成功、5 m、12 s）数值正确 |
| 不允许“sleep 即成功” | 无 Nav2 时每个目标睡 1 s 就上报成功 | 冒烟/launch 测试必须看到真实位姿收敛 |
| 只允许一个速度栈 | bringup 与 tracking 同时启动会有两个 `/cmd_vel` 发布者 | `ros2 topic info /cmd_vel` 发布者数 = 1 |

操作台的判定标准：

| 检查项 | 通过标准 |
|---|---|
| `GET /` | 返回 `front_end.html` 内容（非 404/500） |
| `GET /api/health` | `success=true` 且 `html=true` |
| `GET /api/operator/snapshot` | 有 mission 状态、队列、车队、设施、业务类型字段 |
| `POST /api/business_orders` | 返回 `workflow_order_id`（形如 `business_<单号>`）与 `mission_ids` |
| `POST /api/workflows/*` | 暂停/恢复/取消均 `success=true`（业务拒绝时能读到原因） |
| 缺参数 | 返回 400 而不是 500 |
| 服务未启动 | 返回 503 而不是让网关崩掉 |

以上五条命令全绿，且 8.1~8.6 的验证项逐条通过，才能认为复刻完成。
